# 红圈 club V0.7：管理员签到与真实参与记录

## 交付范围
- 活动管理的「报名名单」升级为独立「名单与签到」页。按报名时昵称搜索、全部/未签到/已签到筛选，显示报名人数、到场人数、未到人数；每页40条。
- 现场管理员确认签到；撤销误签必须填写2—200字符原因；可查看最近20条签到/撤销日志。普通会员不能访问管理接口，门店管理员只能管理本店活动，超级管理员可以管理系统内活动。
- 「我的」新增活动记录入口，区分已报名待签到与已参加；成长履历增加真实参与次数和到场事件。仍使用原永久memberId与活动报名ID。
- 不发放、扣除或修改战力值/魅力值；不修改排行榜、会员身份或兑换规则。
- 不包含二维码签到、无报名的现场补录、活动评价或支付。

## 状态与审计
继续使用 activity_signups.status=applied/cancelled。签到为独立 attendance 子对象：status=checked_in/revoked、version、checkedInAt、checkedInBy、revokedAt、revokedBy、revokeReason、isTest、requestId、signature。

新增 attendance_audit：每次状态转换一条记录，含活动、报名、会员、门店、版本、操作人、服务端时间、原因和前后状态。只保存状态变化；重复请求不重复写日志。测试标记不会自动恢复为正式。

签到/撤销通过服务端事务同时更新报名与审计，并写入 activities.attendanceRevision 作为活动状态竞争的写入保护。客户端必须提交上次读取的expectedVersion和稳定requestId；签名关联操作人、目标和参数。旧请求重放不能把后续已撤销的签到重新签回。

报名与取消也改为事务：同一会员同一活动沿用唯一报名文档；已签到不能自行取消，管理员先撤销误签后才可取消。报名/签到会写活动守护字段，与取消活动/测试标记的活动文档修改产生写冲突，避免快照隔离下的交叉写入。

## 时间、门店与测试规则
- 以服务端时间为准，展示按UTC+8；开场前2小时开放签到，未来更远活动不能提前签到。第一版允许过往已发布活动补签，没有自动结束时间限制，管理员须确认真实到场。撤销在活动取消后仍可操作。
- 管理员权限按活动.storeId，不依赖客户端提交的storeId、role或openid。允许已合法报名的跨门店会员由活动所在店管理员确认，不把会员归属店当作活动权限。
- 新建活动可开启「测试活动」，发布后仍可联调报名与签到，但首页近期推荐/正式参与次数/成长时间线不计入。
- 旧测试活动须在活动管理明确点击「标为测试」；不会根据标题猜测。该入口只允许标为测试，不支持直接恢复为正式。测试内容在操作页面仍保留标识。
- 实际参与查询同时核对当前源活动与报名/签到快照；测试、已取消活动、已撤销签到不计正式参与。取消活动将移出有效成长，原签到及审计保留。
- 成长页每个活动只显示当前有效参与状态：签到后不再重复出现同场报名事件；撤销后参与事件移除，待签到报名恢复。测试操作不会污染正式成长。

## 部署（先备份，再上线）
1. 导出/备份 activities、activity_signups、members，以及原荣誉集合；不删改原会员和身份关联。
2. git pull --ff-only origin main。发生本地冲突先保留本地修改，不能强制覆盖。
3. 新建 attendance_audit 集合，设为「仅管理端可读写」。现有 activities、activity_signups、members、member_identities 也保持管理端读写。
4. 新部署整个 cloudfunctions/activityAttendance 目录（云端安装依赖）。
5. 重新部署 activityAdmin、activityMember、memberGrowth 的整个目录。activityMember 新增 registration.js、participation.js；memberGrowth 新增 participation.js，不能只复制 index.js。
6. 重新编译小程序；上传后在公众平台设置新的体验版，体验成员重新进入。

建议查询索引：activity_signups(activityId ASC,status ASC,_id ASC)、activity_signups(memberId ASC,status ASC,_id ASC)、attendance_audit(signupId ASC,version DESC)。若云环境提示缺少索引，按控制台提示创建，不放宽数据库权限。

## 验收路径
- 我的 → 管理工作台 → 活动与签到 → 选活动 → 名单与签到。
- 创建一场明确开启测试开关的活动，开始时间设在未来10分钟以上、2小时以内。让两名体验员报名，只给其中一人签到。
- 应显示报名2人、签到1人、未签到1人；会员的「我的 → 活动记录」显示测试到场，但成长履历不增加正式参与。
- 重复点击/重复提交不增加记录；对已签到者填写原因撤销后，签到人数归零，其已参加记录转回待签到。再签到也只能算一次。
- 普通会员调用签到接口应拒绝；其他门店管理员应拒绝。测试不要修改真实会员角色或伪造真实数据。
- 第一场真实活动正式结束后验证：实际到场的会员履历增加一条参加记录；误签撤销后同步移除。不要为验收创建虚假的正式参与。

## 测试和限制
node scripts/test-attendance.cjs：45项内存数据库模拟测试。
node scripts/test-attendance-ui.cjs：12项Page/页面结构模拟测试。
另已执行本次JS语法检查及WXML标签结构检查。内存事务模型串行化并发操作，只验证业务防重/回滚约定，不代替真实云数据库的隔离级别、SDK、索引和并发压力测试；也不等同于微信编译与手机验收。

名单与个人有效报名最多扫描1000条，超过明确报错而不是显示不完整人数。名单搜索使用报名时昵称快照，跨分页搜索；到场统计来自同次读取的报名集合，随后其他管理员操作可能使画面过期，应刷新。荣誉读取仍有原先50/100条上限，成长页显示partial提示。

若回滚，请先停止签到操作、保留attendance与审计数据备份；不能直接回滚到允许已签到者自行取消的旧activityMember。会员ID、积分与荣誉数据没有被迁移或重置。
